# Launch checklist

A single pass that confirms every acceptance criterion across **Phases 0–26** still holds — [SPEC](specs/SPEC.md) 0–11, [SPEC-2](specs/SPEC-2.md) 12–17, [SPEC-3](specs/SPEC-3.md)'s trust pass, and [SPEC-4](specs/SPEC-4.md)'s Pillar 4 (18–24) plus the two closing passes — along with the launch-specific gates (offline, audit, crawlability, clean deploy). Run it before announcing. Each box is either a command to run or a thing to verify; the commands are the same gate CI runs.

## The automated gate (must all be green)

```sh
npm run format:check
npm run lint
npm run typecheck
npm run test          # unit + golden corpus + axe accessibility
npm run build
npm run audit         # CSP, no cross-origin loads, provenance, no sensitive persistence
npm run deploy:dry
npm run test:e2e      # Playwright, its own CI job
```

Five more run on a schedule rather than per-commit — three because they need the network and a flaky government site must not fail a build, two because they are slow:

```sh
npm run check:links                        # every external link, monthly
npm run check:adapters                     # every refresh adapter still finds its figure, monthly
npm run check:advisories                   # every npm advisory has a reviewed reason, monthly
node scripts/refresh/watch-sources.ts      # the hand-authored Pillar 4 sources, quarterly
npm run check:boundaries                   # which inclusive/exclusive comparisons any test holds, monthly
npm run check:boundaries:classify          # and, for each survivor, whether a test COULD hold it
```

`check:boundaries` was the only one of these with no workflow behind it, which made "it runs on a schedule" a sentence this file had been carrying without anything to back it. [`check-boundaries.yml`](../.github/workflows/check-boundaries.yml) now runs it monthly, gated on a *newly* unheld boundary the way the others are gated on a new failure.

- [ ] `check:boundaries` reports **no newly unheld comparison** against [`boundary-baseline.json`](../scripts/boundary-baseline.json). It flips every `<=`/`>=` in `src/engine` to its strict form and runs the suite: a comparison whose mutation still passes is a line no test holds. The statutes write these lines "at or below", so `<=` and `<` are different answers to a real person — and an exact threshold is measure-zero for an arbitrary input, so it only ever appears in a case somebody wrote on purpose. **47 of 68 were unheld on 2026-08-30**; **21 after three passes on 2026-08-31**. The first took nine, after [`statutoryThresholds.test.ts`](../tests/engine/statutoryThresholds.test.ts) put a household exactly on nine of them — the 100% FPL floor for the premium tax credit, SNAP's minimum benefit at a household of two, the open-ended top ACA band, Social Security's $25,000/$32,000/$34,000 provisional-income bases, the IRA phase-out endpoints, and the $290-a-week garnishment crossover where the two federal tests agree. Several of those compute the *same dollars* under either reading and differ only in the word beside the number — the tier, the status, which limit binds — which is exactly the class of error a suite of worked examples cannot see. The second took seven more — the thresholds the codebase set for itself (the $1 cliff-noise floor, the AMT screener's zero base and its 85% band, the swept range's top point) plus the January 15 / MLK collision that moves the fourth estimated-tax payment. The third took ten more across the goal plan and the finance engine, where the recurring hazard is that the plan's own advice is a dollar figure — so the person who follows it exactly is the person the flipped comparison fails. Every remaining entry now carries a **verdict, not just a line number**, and the verdict is now **computed rather than read**. `check:boundaries:classify` flips each survivor again and re-runs the engine over the values its comparisons test ([`observe-engine.ts`](../scripts/observe-engine.ts)) instead of the suite — 1.5 seconds a comparison instead of eight. A mutation that moves an observed value is a decision a test could hold; one that moves nothing is a branch whose `else` computes the same answer, which no test can ever hold. **All 21 survivors move nothing, and 0 are observable**: there is no known case left unwritten. That is evidence rather than proof, and what makes it worth believing is the **calibration** — all 47 *held* boundaries must be visible to the same probe, since a test distinguishes them by definition, and the report refuses to be trusted when one is not. It refused twice: eight held comparisons were invisible because the probe stood *near* their thresholds rather than on them, and one because a fixture used a shape `DeadlineDue` does not have and a cast let it compile. Re-run in full on **2026-09-01** — the first complete run under the crash-safe checker — and it reproduces the baseline exactly: 68 comparisons, 47 held, 21 unheld, 0 observable, no miscalibration, no newly unheld, and a clean `src/engine` at the end. The baseline holds the backlog so only a *new* one fails, and it is meant to shrink. Slow by construction (one suite run per comparison), so it runs on a schedule and on demand, never in the unit suite — and since 2026-09-03 that schedule exists, in [`check-boundaries.yml`](../.github/workflows/check-boundaries.yml), which is when the sentence stopped being aspirational. **Re-run in full on 2026-09-03: 71 comparisons, 50 held, 21 unheld, no newly unheld, a clean `src/engine` at the end — and one boundary fixed to get there.** `cliffs.ts:443` had arrived with no case on it, and flipping it did not shift a statutory tax step by one point, it lost the step entirely: with `<`, a sweep point whose taxable income equals the notch fails `prev < notch` and every later interval fails too, so Ohio's $332 is never named and the reader is left with the unexplained drop `findTaxSteps` exists to explain. Four cases hold it now, and the classifier's probe was extended to reach it — a held boundary the probe cannot see is reported as a miscalibration, and that one genuinely was a hole: the probe's sweep stopped at $1,000 and never came near $26,050. It refuses to start if `src/engine` has uncommitted changes, because it rewrites files in place — and, since 2026-09-01, it **survives being killed**. The restore lived in a `finally`, which a signal does not run: Ctrl-C, or a CI job hitting its limit, left one flipped comparison on disk in a file nobody had edited. That state type-checks, builds, and shows a single test failure that reads like a regression somewhere unrelated — the exact class of silent wrong answer this check exists to hunt, planted by the hunter. It was found the way it would be found in practice: a fresh session ran the check, stopped it, and spent the next ten minutes looking at a goal-plan failure caused by a mutation abandoned in `socialSecurity.ts`. Two guards now, because one is not enough. The path being rewritten is **journalled** to `scripts/.boundary-mutation.json` before the rewrite and erased after the restore, so a later run puts back whatever a SIGKILL, an OOM or a closed lid left behind — recovery is `git checkout` on the one path the note names, which is safe precisely because the run refused to start unless that file was clean. And the suite is now spawned **asynchronously** rather than with `execFileSync`: a synchronous child blocks the event loop, so the handler that was supposed to interrupt the eight-minute run sat queued behind it, and the file stayed flipped for as long as anyone was watching. **The baseline is keyed on the line's CONTENT, not its number, since 2026-09-01.** It was `file:line:operator:column`, and a test whose name said the id "survives an edit elsewhere in the file" asserted `x.ts:1:<=:6` — pinning the very line number that made it fragile, which is why nobody noticed. Adding two unrelated functions to the engine that day shifted three boundaries: each read as **newly unheld** (the failure that means a threshold arrived with no case on it) while its twin read as **held now, remove it**, and accepting that report would have deleted the written reason each entry carried. The id is now file, operator, column, and a hash of the line's own text — an edit elsewhere leaves it alone, an edit to the comparison's own line changes it, which is when a person should look again; all twenty-one reasons migrated, none lost. **That fix then broke the checker in the most dangerous direction available.** The mutation wrote its operator at `Number(id.split(":").pop())` — the column under the old id shape, a hash under the new one — so every flip landed at column `NaN`, mangled its line, failed to compile, and made the suite fail for a reason unrelated to the comparison. The report came back **"70 are held by a test · 0 are not"**: a perfect score, from a check that had stopped checking. It was caught by not believing it — flipping the MLK January-21 line by hand, the one proved unreachable that morning, and finding the suite green where the report insisted it should be red. The column is a field on the boundary now, with a test that it indexes to the operator. An id is an identity, not a place to keep data the code needs; and a mutation checker reporting that everything is held is far more likely broken than triumphant. The classifier was re-run afterwards, with a mutator that works, and returned the same verdict it had before the bug: **0 observable · 21 with no observed difference**. The baseline's reasons therefore stand on two independent legs — a person reading each line, and a probe that moves nothing when the line is flipped. **The twenty-one survivors were read line by line on 2026-09-01 and every one carries the reason no test holds it**, in the baseline itself, under the rule `watch-coverage.json` already applies to an unwatched dataset: a reason is a decision someone can argue with later, not a shrug. The classifier had said "no observed difference" for all twenty-one; what it could not say is *why*, and the three kinds are different work. **Seventeen are equivalent** — the `else` arm computes the same value at exactly that point, so asking for a test is asking for a fixture that manufactures a difference. **Three are unreachable**: `iraDeduction`'s guard against a zero it is never handed, `finance.ts:736`'s second clause that the first has already returned on, and a tie between the AOTC and the Lifetime Learning Credit that their own arithmetic keeps apart. **One is correct and unreachable**: `dueDates`' `date <= 21` really would misclassify Martin Luther King Jr. Day in 2030 and 2036, and no deadline this engine computes can land on January 21 to notice — holding it would mean exporting a helper for the test's benefit rather than a reader's. So the list should still shrink, but not by writing twenty-one tests; it shrinks when one of those functions gains a caller that can reach the line. A new entry now records with an **empty** reason, which the baseline's own test rejects until a person writes one, so recording costs a sentence. And a **`--file` run now speaks only about the file it checked**: it had been reporting every *other* file's baseline entries under "held now — remove them from it", which is an instruction to empty the baseline of twenty-one lines nothing had re-examined, after which the next full run would fail on all of them as newly unheld. Scoping narrows what a run may claim, not what it may catch — a boundary newly unheld inside the scope still fails it.

Self-Employed Retirement applied limb (A) alone: an employee deferral capped at net earnings, plus an employer share of 20% of the same net earnings. Measured, not inferred — at **$10,000 of profit it offered a solo-401(k) ceiling of $11,152 against $9,294 of net earnings, 120%**; at $30,000 it offered 107.9%. Both are over the limit, in the direction that costs money: an excess contribution is a correction, 10% under §4972 on the employer side, and 6% a year under §4973 on what stays. The tile's own explainer recommended the solo 401(k) "especially at low-to-moderate profit" — the exact range it was wrong in. **And the answer is not `min(total, net earnings)`.** Earned income is net earnings reduced by the contributions made for the participant (§401(c)(2), and the IRS states it the same way for one-participant plans), so the employer share shrinks the compensation the limit is measured against while elective deferrals do not — §404(n) keeps them out of the deduction limit and out of its application to other contributions. A scope that stops at a directory boundary is a coincidence, not a scope. **The Act rewrote charitable giving in two directions and only the generous half was modeled.** §170(b)(1)(I), added by the same §70425 for taxable years after 2025, allows an itemizer's contributions "only to the extent that the aggregate of such contributions exceeds 0.5 percent of the taxpayer's contribution base for the taxable year" — the base being AGI without a net operating loss carryback (§170(b)(1)(H)). The engine deducted giving in full, so the itemized deduction was too LARGE, which is the direction worth naming: every other correction on 2026-09-01 gave a reader money back, and this one takes some away. A tool that only ever finds errors in the taxpayer's favour is not checking, it is flattering. The golden case at $200,000 with $5,000 of giving moved from $43,000 of itemized deductions to **$42,000**. It does **not** reach §170(p), and that is the statute's own instruction rather than a reading: §170(p) computes its figure "determined without regard to subsections (b)(1)(G)(ii), **(b)(1)(I)**, and (d)(1)". So the same $1,000 of giving is now worth more to a filer who does not itemize than the first $1,000 is to one who does — pinned by a case, because it looks like a bug. The floor also moves the auto standard-versus-itemized choice, which has its own case. The AGI *ceilings* on giving (60% for cash, 30% for appreciated property) stay out of scope: one `charitable` input cannot tell the two kinds apart. **All six of the Act's amendments to §170 were then read, not just the two that were obvious**, because a section amended by four different sections of one bill is a section worth finishing. §70425(a)(1) added the floor and (a)(3) is what inserted "(b)(1)(I)" into subsection (p) — so the exemption this engine relies on is the Act's own edit rather than a reading of surrounding structure. §70425(b)(1) made the 60% cash ceiling permanent, which changes nothing here because the ceilings are already out of scope. §70426(a)-(c) rewrote §170(b)(2) and (d)(2), which are **corporate** contribution rules and do not reach an individual return. §70429(a) raised §170(n) from $10,000 to $50,000 — the deduction for expenses of Native Alaskan subsistence whaling captains, which this engine has never modeled and does not pretend to. That leaves exactly one individual-facing omission from the whole section: §70425(a)(2)'s new §170(d)(1)(C), the **carryover** rule for giving that exceeds the ceilings, which this engine cannot model because it carries no concept of a prior year at all. **§199A was checked the same way, because two tiles quote its 20%** and the Act amended it: §70105 widened the phase-in range to $75,000/$150,000 and added a minimum deduction under a new subsection (i), and §70201(d) added §199A(c)(4)(D) — but the **20 percent is unchanged**, so "we don't subtract the QBI deduction, so this errs a little high" on Quarterly Taxes and the self-employment tiles is still both true and correctly stated. A sweep that finds nothing is still worth recording; otherwise the next person repeats it. §170 joins the change-watch as the fourth statute on this shard. **IRC §68 is back too**, and 2026 is the first year in eight that it does anything: the pre-Act version applied to no taxable year from 2018 through 2025, and §70111 rewrote it generally with effect from 2026. It is no longer a phase-out of the deductions but a cap on their **value** — reduce them by "2/37 of the lesser of (1) such amount of itemized deductions, or (2) so much of the taxable income ... as exceeds the dollar amount at which the 37 percent rate bracket ... begins". Two thirty-sevenths of 37% is 2%, so a dollar of deduction saves a top-bracket filer **35 cents rather than 37**, and that identity is the first test: if it ever reads 37, the section has stopped working. The fraction is on the shard as the **numerator and denominator the statute writes**, because 2/37 does not terminate and a rounded decimal would be a figure nobody could reproduce from the Code; the threshold is not on the shard at all, because it is the start of this shard's own 37% bracket and a copy would be a second thing to drift. §68(b) applies it after every other limitation, so the engine reaches it last — after the SALT cap, the charitable floor and the medical floor. Both arms of the "lesser of" have a case, because a filer only just inside the top bracket has little income up there for the deduction to be over-valued against. And because `amount` is the figure *after* the reduction — it has to be, or AGI minus the lines shown would not equal the taxable income beside them — **what §68 took back is reported as its own figure** and rendered as a line when it is not zero. Otherwise a filer who typed $60,000 of mortgage interest reads a $56,756.76 deduction with nothing on screen accounting for the difference, which is the opposite of showing the work. The lines are absent for every reader below the 37% bracket, which is nearly all of them, and when present they run **gross, reduction, net** in that order — a reduction shown *after* an already-net figure reads as a second subtraction the reader is meant to make themselves. Verified in a browser: $900,000 of wages and $60,000 of mortgage interest renders $60,000.00, −$3,243.24, $56,756.76, and a taxable income of $843,243.24 that reconciles against the AGI above it. §68 also creates a **marginal rate that appears in no rate schedule**, and the engine's $100 probe finds it without being told: while clause (2) binds, another dollar of income raises the reduction by 2/37 of a dollar, so taxable income rises by 1 + 2/37 and the bracket rate is multiplied by **39/37** — 36.89% of federal tax inside the 35% band, 39.00% inside the 37%. Neither is a figure anyone legislated or a reader could find in a table, both are exact, and a case pins them because a second-order effect that the probe stopped seeing would otherwise fail silently. §68 is the **fifth** statute watched on this shard, and it is watched precisely because a section dormant for eight years is the one nobody notices changing again. **§163(h)(4) — car loan interest — was the fifth, and it was missing from the list of four**: the Act's §70203 takes qualified passenger vehicle loan interest out of the personal interest §163(h)(1) disallows, and §63(b)(7) reaches it for a filer who does not itemize, so up to **$10,000** a year comes off either way. It lives on the Federal Income Tax tile, beside mortgage interest but outside the itemized group, because the choice does not affect it. Two readings that "it is the same shape as tips and overtime" gets wrong, each with a case: (C)(ii) says "$200 for each $1,000 **(or portion thereof)**", so a filer one dollar into a thousand loses the whole $200 where a tipped worker in the same position loses nothing — a **fourth phase-out shape** in one Act — and the section carries **no joint-return restriction**, so a married individual filing separately is eligible at the $100,000 threshold where §224(f) and §225(e) would give them zero. That step is a **cliff, not a slope**, and the engine's own marginal probe says so: a single filer at exactly $100,000 with a car loan sees **73.65%** on the next hundred dollars — 29.65% of ordinary tax and FICA, plus 44% from $200 of deduction lost on $100 of income — and 29.65% again a hundred dollars later. The figure is correct and startling, so it is pinned by a test rather than left to surprise someone, and the explainer warns the reader before the tile does. Both are now **fields on the shard** (`partialStepCounts`, `jointReturnOnly`) rather than a convention the engine applies to every rule of that shape, so the next same-shaped section has to state its answer. The Auto Loan tile, which computes the interest figure the deduction is measured on, names the rule and **hands the figure over** — a "Deduct this interest" button that opens Federal Income Tax with the amount already in the field. It carries the **first twelve months'** interest and not the total cost of credit, because §163(h)(4) deducts interest paid *in the taxable year*: on the tile's own example those are $2,300 and $8,100, so the obvious copy-and-paste would claim a deduction more than three times too large. The first year is also the largest, which makes it the year that says whether the $10,000 ceiling is anywhere near. A loan that did not start in January pays less inside one calendar year, and the explainer says so. **The e2e caught that the button did not work at all**, which the unit test could not: it asserted the callback's arguments, and the arguments were right. A calculator is not a route — `federal-income-tax` lives at `#/paycheck-taxes?tool=federal-income-tax` — and the hub remapped `navigate(<id>)` only for **its own** sub-tools, so a cross-hub target fell through to a tile id the router cannot resolve and dropped the reader on the home page. The same remap also **threw the caller's params away**, so a link carrying a value would have arrived empty even inside one hub. Both are fixed at the hub, using a new `hubIdForTool` on the registry, so every tile's `ctx.navigate` is now reliable rather than reliable-if-the-target-is-a-sibling — and its three quoted figures joined [`proseFigures.test.ts`](../tests/ui/proseFigures.test.ts) rather than being trusted, because a second file quoting a shard is a second place for it to go stale. **The Readout closes the loop**: tax year 2026 added W-2 **box 12 codes TP and TT** (IRS *General Instructions for Forms W-2 and W-3*, Rev. 1-2026) precisely so the figures §§224 and 225 deduct appear on the form, and both now extract into My Situation and pre-fill Take-Home — a tipped worker who drops in their W-2 does not retype two numbers off the paper they just handed us. The whole path is exercised end to end in a real browser now — a 2026 W-2 dropped on the Readout, both boxes recognised, confirmed into My Situation, and Take-Home opening with $14,000 of tips and $3,200 of overtime already in its fields. Every step of that was unit-tested in isolation and none of it had ever been run as one path. **TT is read as the deduction; TP is read as a ceiling**, because the box holds "total amount of cash tips reported to the employer" while §224 reaches only Treasury-listed occupations, which is what the new **box 14b** occupation code (`000` for a nonqualifying one) records. Both anchors demand the code as a word after a box-12 subscript: "TP" and "TT" sit inside ordinary English words, and reading an amount after a stray one is the inference this module exists not to make. A W-2 from an earlier year carries neither code and the extractor drops what it cannot read, so a prior-year document never arrives claiming the reader had no tips. **Box 14b is extracted and checked**: a `000` there is the employer stating that some of the tips were received in a nonqualifying occupation, so the answer asks "do all of these tips qualify?" against the IRS instruction that requires the code — a `rule` check with a citation, suppressed on OCR because three digits are what a scan gets wrong and the claim is about someone's occupation. The Treasury occupation list is deliberately not bundled: it changes by notice, and a stale copy would let this site deny a deduction someone is owed.

- [x] **Production responses carry the security headers — as of 2026-09-03 they did not, and this is the fix.** `https://enklayve.com/` was answering with **no Content-Security-Policy, no HSTS, no Referrer-Policy and no X-Content-Type-Options**, on `/`, `/index.html`, `/robots.txt` and `/tools.html` alike, cache busted. The cause is a default in Workers Static Assets: a request matching a file under `[assets] directory` is answered by the asset server **without invoking the Worker**, so `worker/index.ts` — where every one of those headers is set, including the `connect-src 'none'` this project's entire privacy claim rests on — never ran for any real path. It was true of the code and absent from the site, and every check in this repo passed throughout, because they all read the code that sets the headers and nothing asked whether it runs. **`run_worker_first = true`** puts the Worker back in front of every request; it serves the same bytes through `env.ASSETS.fetch` and decorates them. Held by [`workerRouting.test.ts`](../tests/build/workerRouting.test.ts), which reads the config with comments stripped so a rule described in prose cannot pass for a rule set. **The live check has to stay a live check**: no unit test can reach production, and this is precisely the class of failure that only production shows — so it is a command now rather than a box somebody ticks. `npm run check:live` asserts the header family against the response, that the shell is not pinned by a hard cache, and that a missing hashed chunk is a 404 rather than the app's home page wearing its URL. It runs weekly and on demand, opens an issue when production stops matching the repository, and takes an origin so a staging deploy can be checked the same way. Its report names `wrangler.toml` rather than the header code, because the header code was right the whole time.
