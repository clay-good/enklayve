# Data sources

Every number enklayve shows is computed from a **bundled, versioned dataset** with a full citation — never fetched at runtime (the CSP sets `connect-src 'none'`) and never guessed. This document lists the sources, their refresh cadence, and how the data layer keeps them honest.

The authoritative, machine-readable record is [`data/manifest.json`](../data/manifest.json): every shard is pinned there to a version, an effective year, a source URL, a source document name, a retrieval date, and a SHA-256 content hash. The build embeds the manifest so the running app knows exactly what it is computing from, and the release audit (`npm run audit`) fails the build if any shard is missing a citation (the no-orphan-numbers rule, SPEC §9).

### Source audits

The refresh adapters watch a source for movement; they do not re-read it against the shard. So a figure transcribed wrong, or one that indexed while the adapter was watching a page that did not visibly change, can sit correct-looking for a long time. Two automated checks stand behind them. `npm run check:links` reports any cited URL that 404s **or redirects** — it now sweeps `scripts/` as well as `src/`, `data/` and `docs/`, because an adapter's watched URL lives nowhere else and four of them had been pointing at 404s unnoticed. `npm run check:adapters` goes further: it runs every adapter's parser against its live source and reports which ones can still find their figure. Both send a browser user agent — government WAFs refuse anything else, sometimes with a 403 and sometimes with a 200 carrying a challenge page, which is worse because it looks like success — and both read **PDFs**, using the same pdf.js the app ships for a user's own documents. That last one is not a nicety: Illinois states its exemption in a bulletin, Michigan its rate and exemption on page one of Form 446, Maryland its 24 county rates in Withholding Tax Facts, Rhode Island its indexed brackets in an advisory. While the pipeline could only read markup, every one of those shards was unwatched. It reports each adapter as agreeing with its shard, proposing a change, unable to parse, or unreachable — where **unreachable also covers a source that answered and declined to serve**: the BLS CPI API is keyless at a small daily quota counted per IP, a CI runner shares its IP, and a spent quota comes back `200 OK` with valid JSON, no series, and BLS's own `REQUEST_NOT_PROCESSED` message. Filed as a parse failure that reads as "the API changed shape" and sends a reader to rewrite a parser that is fine; the check now repeats what BLS said, and a registration key is the remedy. Unreachable now splits again, because two things were sharing one heading and one of them is not weather: a server that does not serve a complete certificate chain will be refused by Node every run forever, so its shard has stopped being watched **permanently** while the report says the source may be having an afternoon. Mississippi's DOR is that case, and the adapter check could not even say so — Node reports every transport failure as `fetch failed` and hides the reason in `cause`, so the monthly report read `fetch failed: fetch failed` while the link check on the same server named the certificate. The cause chain is unwrapped now, the certificate pattern lives beside the shared fetch so the two checks cannot disagree about the same server, and the permanent case is reported under its own heading. It is not gated: it fails every run by definition, and an alarm that always fires is not an alarm. Mississippi then stopped being that case. `*.ms.gov` is one estate — Revenue, the Legislature, all of it, run by the state's Department of Information Technology Services — and every host presents the leaf alone, omitting the GlobalSign intermediate that signed it, so there was no other Mississippi source to repoint to. A browser closes that gap by following the leaf's Authority Information Access pointer and fetching the missing certificate, and the shared fetch now does the same ([`chain-repair.ts`](../scripts/chain-repair.ts)), only after a chain failure has already been diagnosed. The security-critical line is that the fetched certificate is not taken on faith: everything in a CA bundle is a trust anchor, so it is added only if a certificate already in Node's root store signed it **and** it is the certificate that signed this leaf — the ordinary condition every other chain has to meet. The unverified connection exists solely to read the AIA pointer; nothing it returns is used as data, and the request that carries the page is verified in full, hostname included. **Mississippi is watched for the first time**, and it is a state that needed watching: HB 1 (2025) steps its rate down every January — 4.4% for 2025, 4% for 2026, 3.75% for 2027 — so the shard goes wrong on a schedule. Its adapter moved to the page the shard already cites (*watch what you cite*), and it reads only the by-year table there, because the same section states two other rates that look exactly like this figure: a lead sentence opening "In 2026, the graduated 2025 tax year income tax rate is: ... 4.4% on the remaining taxable income in excess of $10,000" — the shard's year in its first two words and the previous year's rate, which is DOR describing the return filed during 2026 — and "The 4% rate is eliminated for tax year 2024 and forward", where "4%" names the abolished bracket *below* $10,000, the same characters meaning the opposite. The shard's own year picks the row, and two rows are required, because one "Tax Year … taxed @ …" is a sentence and a sequence of them is a table — and — since an unreachable source is the agency's afternoon rather than a defect — never lets one gate, including for an adapter already on the watched list, which it used to: a single dropped connection under six-way concurrency took Pennsylvania out of the anchoring set and reported it as a shard that had stopped being watched, and it anchored fine on its own a minute later. A watched adapter nobody reached is now listed as not reached, the fetch retries once the way the link check has always done, and gates on a committed **known-anchoring baseline** ([`adapter-baseline.json`](../scripts/refresh/adapter-baseline.json)) rather than on the raw count — forty-odd cannot anchor today, and an issue listing all of them every month is the alert people learn to close unread. The baseline deliberately holds the SHORT healthy list, which should grow; only an adapter falling out of it fails the check. That check's first run, on 2026-08-29, found roughly **30 of 49 adapters no longer anchoring** — the mechanical explanation for how Illinois, Michigan, Missouri and Georgia went stale. Both run monthly on a schedule, never in the unit suite. One caveat matters: **"anchored" means the parser found something shaped like its figure, not that the value is right.** Pointing Maine's deduction adapter at the 2026 Form 1040ES — a document that genuinely does state the deduction — made it "anchor" $49,824 for single and $5,300 for married jointly, a bracket threshold and the personal exemption scraped off a page dense with numbers. Nothing downstream would have shipped those; the refresh only proposes a PR, the golden suite gates it, and a person reviews. But repointing an adapter means dry-running it and reading the diff, never watching the check go green.

A third check is the one that reads what an adapter would actually *write*: `node scripts/refresh/run.ts --adapter <id> --dry-run` now prints the diff, not just the outcome word. Running it across all 49 on 2026-08-29 found **nine adapters that would have proposed wrong values** — California's standard deduction anchoring `2019` and Delaware's `2014` (page furniture read as dollars), Rhode Island reading the 2025 column of a two-year table, Medicaid proposing 138% → 133% of the poverty line (the effective figure replaced by the statutory one, about $800 of annual income for a household of one), the I-bond fixed and inflation rates both anchoring the composite rate, and Iowa proposing a rate repealed in 2024. The golden gate would have blocked most of them, which is the fail-safe working — but a proposal that survives to a PR is a proposal someone might approve. Each is now a refusal with a reason: a plausibility band on deductions, a two-column guard, an ambiguity guard on rates, a collision guard on the I-bond components, and for Iowa a flat refusal, because its DOR page states a repealed figure that parses perfectly and no generic guard can tell it from a real rate cut. (Iowa's refusal has since been resolved the way it asked to be: the adapter watches the IDR's own 2026 rate announcement, which states the 3.8% that is actually law.)

The same dry run suggested one repair for why so many cannot parse at all. **Twenty-one adapters watch a landing page while their shard cites the actual document** — the bulletin, the withholding formula, the rate schedule the figure was transcribed from. The landing page is a menu; the cited document states the number, so pointing the adapter at what the shard already cites should be both the fix and the invariant: *watch what you cite.* Running every adapter against its own cited document put that at **two of the twenty-one** (Kentucky and Iowa). The other nineteen refuse, and the refusals are the guards working — California's 540 rate-schedule PDF offers `540` as a standard deduction, Wisconsin's Form 1-ES offers `2026`, Vermont's schedule and Oklahoma's legislative update each state two candidates. A form dense with numbers is not a better source than a menu with none; it is a worse one, because it parses. Repointing is a per-adapter judgement, not a sweep. The second cause is shape: a flat-rate state usually publishes its rate in a **table**, so the fetched markup is now reduced to visible text before matching (which also drops a page's stylesheet and meta tags, where one stated rate could match four times). A rate *history* table is the trap on the other side — Colorado's guide lists a rate per year since 2019, and every pattern reaches the first row — so a number introduced by a bare year is refused outright, while a sentence that names its year ("the income tax rate for 2026 is 2.95%") still reads. Illinois, Arizona, Kentucky and Iowa joined the baseline on 2026-08-29, taking it from five adapters to nine. The federal shard makes ten, and it was the worst case of all: its adapter watched **Rev. Proc. 2023-34** — the 2024 revenue procedure — for a 2026 shard, a document frozen three years ago that reports agreement forever and can never report a change. It now reads the current procedure with a parser that takes both anchors from the document: the shard's own tax year selects the table (a revenue procedure states the new year's *and* the one it replaces, identically labelled), and each row is matched on the statutory subsection it cites, `§ 1(j)(2)(A)`–`(D)`, the only thing that distinguishes the two $16,100 rows. A procedure that does not state the shard's year is refused by name. The HHS poverty guidelines are the same lesson again, on the most load-bearing figure the site carries: HHS issues **three** guidelines — contiguous, Alaska, Hawaii — and prints them on one page in identical format, so the old parser took the first "1 $…" row and the first increment sentence from anywhere on it, and Alaska and Hawaii had no adapter at all. Each shard names its own `region` and `year`, and those select the section, so all three are watched. SNAP was the same story with a twist: the source was never the problem, only the page — the per-fiscal-year COLA page renders its tables client-side, while the COLA index states them in the markup as one country-wide table with a column per region, so the parser reads the header, lets the shard's region pick a column, and refuses a row that is not the header's width. The I-bond adapter's collision guard was right about a wrong premise: the semiannual inflation rate is not on the page at all. TreasuryDirect states the composite rate, the fixed rate, and the period, so the fixed rate is written and the inflation rate is only *checked* against Treasury's composite formula — and the period is anchored, so a newly-announced six months is refused by name rather than written over the previous one. And four came from reading the shards instead of the pages: nine states' standard deductions are identical to the federal one because they *are* the federal one (the conformity pattern the shards' notes describe), and four of those — DC, New Mexico, Montana, North Dakota — had adapters asking a state DOR page for a figure it would never state. They read the IRS revenue procedure now. Michigan's figures were never on a web page: they are the masthead of Form 446, which is what the PDF support was built for — read by a dedicated parser, because "withholding rate" is only the income-tax rate in a state whose statute makes them the same figure. New York and North Carolina followed once the deduction parser stopped reading raw markup, stopped reading the row that states a *dependent's* deduction (a smaller number under the same label — reaching it yields not a figure that looks wrong but one that looks like a stingier state), bounded how far a status label may reach for an amount, and learned to read only the table on a page that announces one. California followed, and picking its source shows why "a page that states the figure" is not the whole instruction: its 2026 Form 540-ES instructions state the right numbers amount-first ("$5,706 single or married/RDP filing separately $11,412 married/RDP filing jointly"), where a label-then-amount pattern reads single's deduction as $11,412 — so the adapter watches the FTB deduction chart, which states them the right way round. Maine came next, and its rate schedule broke the table-narrowing three separate ways at once: its lead-in is a bare colon ("Standard Deduction: Single - $15,700 …"), it *mentions* the standard deduction's inflation factor 1,500 characters before it states the table, and it prints the **additional** amount for age and blindness — $1,650 / $3,300 / $6,600, in a sentence containing "married … filing jointly" — inside 400 characters of the table, which made $3,300 a second joint candidate and refused the page. So the region is now the first lead-in that has a status label and an amount actually under it, and it ends where the age/blindness add-on begins. Maine's own documents also disagree with each other: the December 2025 withholding booklet states a $15,300 / $30,600 basic standard deduction, while the rate schedule revised 2026-05-20 and Form 1040ES-ME revised July 2026 both state $15,700 / $31,400 / $23,550 — which is what the shard carries. The adapter and the citation now point at the rate schedule, the newest document that states all three. Rhode Island followed from the same reading. Its inflation advisory (ADV 2025-22) prints "Filing status 2025 2026 / Single $10,900 $11,200 / Married filing jointly* $21,800 $22,400", and the side-by-side guard refused it outright — correctly, while nothing said which column was which. But the header says which column is which, and the shard knows its own tax year, so the shard picks the column: the same anchor the federal revenue procedure and the SNAP region tables already use, and the reason those are watched rather than refused. A table with no year header, or one whose header does not name the shard's year, is refused exactly as before — and the refusal now names how many amounts it found and shows the first three, because Kansas' book runs a whole tax table into one row and the old message printed a hundred and fifty numbers at a reader who stopped at the third. Georgia is the California failure with no way out: it states its figures amount-first — "Georgia standard deductions have increased to $30,000 for taxpayers filing Married Filing Jointly and $15,000 for Single, Head of Household, and Married Filing Separate taxpayers" — in the Employer's Withholding Tax Guide *and*, in nearly the same words, on the Important Tax Updates page, so unlike California there is no document stating them the right way round to repoint to. It gets a parser for the sentence's real unit, an amount and the list of statuses it applies to, which is also the only way to read the thing that makes Georgia unusual: the deduction does NOT double for head of household there — head of household takes the single amount, like married filing separately, so a parser assuming the federal 1.5x shape would be wrong by $7,500 while looking healthy. Adding amount-first as a general fallback was the other option and is worse: the two readings disagree on Georgia's own sentence (label-first, "Married Filing Jointly" reaches forward to $15,000), so no both-must-agree rule keeps it, and on a label-first page an amount-first pattern reads every figure off by one row. The guide's own year is checked against the shard's, the Form 446 rule. Massachusetts was demanding a figure its source never had: the DOR surtax page is about the surtax and states no base rate — the only "5%" on it is the elective pass-through excise, in an FAQ answer explaining that the excise is not the surtax — so the adapter reported a moved source about a page that states exactly what the shard carries. The 5% base is statutory (M.G.L. c. 62 §4) and now comes from the shard; the page supplies the surtax rate and the threshold, which it states as a by-year list ("Tax year 2026 is $1,107,750 / Tax year 2025 is $1,083,150 / …"), so the shard's year picks the row and a list that stops short of it says so. New Jersey was watching the page that links to its rate schedules — a menu of PDFs by year, stating no bracket — while the schedule itself states the top tier in the arithmetic a filer works through: "$1,000,000 and over __________ .1075 = __________ – $ 32,926.25", threshold first and the rate as a decimal. It reads that form now, from NJ's stable `pdf/current/njtaxratesch.pdf`, and requires the two tables (single and joint) to agree on the tier before writing it. South Carolina turned out to be the same shape as Georgia — H. 4216's announcement states the new SCIAD amount-first ("$15,000 for taxpayers who file as single or married filing separately $22,500 for taxpayers who file as head of household $30,000 for taxpayers who file as married filing jointly"), which is why label-first read head of household as $30,000 and the drift guard refused it. It reuses Georgia's parser; the annual-masthead check is now a parameter, because Georgia's guide is reissued each year at a year-stamped URL and a one-off bill announcement has no masthead to carry. Arkansas, Oklahoma and Wisconsin were checked for the same shape and do not have it. Wisconsin states no standard deduction as a figure — it states four sliding schedules, and the number the shard carries is the maximum, which is the third cell of the first row ("$ 0 $ 20,119 $ 13,960"). No label-then-amount pattern reaches it: "Single" is eighty-five characters and a column heading away from anything shaped like dollars, and the first thing it reaches is the $0 that opens the income band. Worse, "Schedule for Married Filing Separately" ($12,280) sits directly under "Married Filing Jointly" ($25,840), and nothing in a shared pattern keeps `married … jointly` out of the wrong schedule. So the schedules are addressed by name and the row is read positionally, gated on the form stating "The 2026 Standard Deduction is" — Form 1-ES is reissued each year at a year-stamped URL, the Form 446 rule. Missouri came back by moving to the document its shard already cited. Its Withholding Tax Formula states the same ladder as the year-changes page and states its year, but splits it across two rows — "Rates 0.00% 2.00% 2.50% … 4.70%" and, four hundred characters and four other payroll frequencies later, "Annual Payroll $ 0.00 to $1,348.00 1,348.01 to 2,696.00 …". No rate-in-excess-of-a-threshold pattern can pair those, so they are read as two rows and zipped, and the count is checked against each other and against the committed schedule before anything is written. A band's opening cent is its predecessor's ceiling plus a penny, so bounds dedupe on the dollar. West Virginia reads its published table as rows: the page states each rate's floor twice — once to open the band, once as "of the excess over" — and the second is the authoritative pairing, because it sits in the same clause as its rate. That is what keeps the base rate out of the second bracket where three separate things anchor at $10,000, and the read stops where the married-filing-separately schedule begins. Medicaid's 133-against-138 is filed as settled for that pair only: two correct statements of one rule that need nobody, while any other disagreement is a surprise that wants a person now. **42 of 59 adapters watch their shard, and the check's "could not anchor" section is empty for the first time** — and `settled` reaches the refresh job as well as the report: a settled refusal is a fifth terminal outcome beside open-pr / alert-pr / blocked / no-op, so it leaves the shard alone exactly as an alert does but opens no pull request and writes no diff-log entry. Without that, every scheduled run opened seventeen fail-safe alert PRs saying "source unreachable or failed validation" about sources that are neither. A fetch failure is never settled: the adapter never got to answer — every remaining adapter refuses for a stated reason or could not be reached. The last three "could not anchor any standard-deduction figure by filing status" entries turned out to be three different kinds of nothing to anchor. **Arkansas** has not published its 2026 forms — DFA's newest is the 2025 set, and the shard carries the 2025 AR1000F figures forward deliberately. **Oklahoma** froze its deduction at the 2017 federal amounts under 68 O.S. §2358 and it has not moved since. **Maryland's** is a statutory cap on a percentage rather than an amount: the deduction is the lesser of 15% of Maryland AGI or $3,350 / $6,700, caps the 2025 session set. A ladder assembled from a collision is wrong in the way nothing downstream can see: right shape, right thresholds, one rate off. Colliding thresholds are now a refusal that names both rates. Alabama joined the settled list rather than the watched one, and the reason is worth recording: it states no standard-deduction figure anywhere. The shard's year now picks the block. The same change nearly caused the worst failure in this log: with visible-text reading, Missouri's undated ladder parsed cleanly and proposed rolling every threshold in the state back a year under a live citation. Refusing every undated schedule would have been the wrong correction, because confirming is always safe while changing on an undated page never is. (The state that motivated the carve-out was Mississippi, whose rate had no year to state; it has since moved to a dated by-year table and its own parser, so the rule is now carried by its test rather than by any live source.) A **source audit** is the manual counterpart: open the state's own published form and check the shipped shard against it, line by line. ## The fail-safe contract (SPEC §7.3)

A refresh job fetches the source, parses it with a source-specific adapter, emits normalized JSON plus a content hash, appends a human-readable diff, and runs the full golden suite. It opens a PR **only if tests pass and values changed**; if a source 404s or fails schema validation it opens an *alert* PR that flips the affected rules into fail-safe mode rather than shipping a wrong number. Data is never auto-committed to `main` without passing the test gate. At runtime, a shard whose effective year is older than its refresh window — or whose hash fails — is marked **stale**, and the tiles that depend on it surface a "verify before relying" banner instead of presenting a number as current.

This contract is implemented under [`scripts/refresh/`](../scripts/refresh/): a pure, unit-tested harness (`contract.ts`: the diff and the open-PR-vs-alert decision), the source adapters (`adapters.ts`: IRS, BLS CPI, SSA, HHS, the TreasuryDirect I-bond rates, USDA SNAP, CMS Medicaid, and **one adapter for every one of the 41 income-tax states + DC**, grouped by shape — standard-deduction parsers, flat-rate parsers, graduated bracket-table parsers (e.g. Ohio / Mississippi's "0% then a flat rate over a floor" schedule), and dedicated special-case parsers (Massachusetts's 5% base + 4% surtax, New Jersey's per-status schedule, Connecticut's recapture, and the rest) — each anchoring to known labels and flagging rather than guessing when a layout changes; the full roster is pinned by [`tests/build/dataRefresh.test.ts`](../tests/build/dataRefresh.test.ts)), and the runner (`run.ts`). With this set, **every seeded jurisdiction with an income tax has a refresh adapter, and every one of the 50 states + DC is modeled.** One GitHub Actions workflow per source group (`.github/workflows/refresh-*.yml`) runs on the cadence above and on manual dispatch, gates every data PR on the golden suite, and writes each change to the [source diff log](source-diff-log.md). The adapters refresh the committed figures in place; rolling a shard to a new effective year and transcribing a full bracket table remain the reviewer's data-only step on the resulting PR (see [`adding-a-state.md`](adding-a-state.md)).

### The source watch

Six shards carry prose transcribed from statutes and government consumer pages rather than a table of figures: `bill-triage`, `free-filing`, `no-surprises`, `garnishment-limits`, `enrollment-windows`, and `life-events`. They are refreshed by **review, not by parsing**.

`watch-pillar4-sources.yml` runs quarterly, fingerprints the visible text of each source (`scripts/refresh/source-watch.json` holds the last-reviewed fingerprint and the reason that shard cannot be auto-parsed), and opens an issue naming the shards whose sources moved. **It never edits a shard.** Six of the eight entries are hand-authored Pillar 4 shards. The other two were added 2026-08-30. One is **Medicaid's expansion map** (below). The other is **Delaware's income tax**, which arrives from the other direction: its standard deduction is statutory and unindexed — 30 Del. C. §1108 has set it at $3,250 / $6,500 since tax year 2000 — so an annual value adapter asks a question with no annual answer, and the section states the amounts as a history of periods without ever using a filing-status label a parser knows. A change there is an amendment, and an amendment is read, not parsed. Auto-rewriting a sentence about what a federal protection covers, from a scraped page, is the failure this design exists to avoid.

**Three statutory shards that Delaware's treatment does not reach (searched 2026-08-30).** Alabama, Oklahoma and Maryland are settled for exactly Delaware's reason — Ala. Code §40-18-15 was last raised by Act 2022-292, 68 O.S. §2358 froze Oklahoma's deduction at the 2017 federal amounts, and Maryland's is a statutory cap the General Assembly sets — so each ought to join the change-watch beside it. None can, and the reason is worth recording so the next person does not repeat the search. Justia returns 403 to this pipeline for both Alabama's and Oklahoma's sections; Alabama's own `alisondb.legislature.state.al.us` no longer resolves; Maryland's `mgaleg.maryland.gov` statute-text endpoint answers "Bill number does not exist"; and Oklahoma's Senate publishes Title 68 as one 3.7 MB PDF, where a fingerprint would fire for any change to any section of the title and mean nothing. Alabama's Form 40 booklet *is* readable and does contain the chart, but its URL carries the year, which makes it a closed document — a watch on it could never fire, the Rev. Proc. 2023-34 trap wearing a third disguise. A watch that cannot fire is worse than none, because it reads as coverage. So these three stay watched by nobody, knowingly, until a stable fetchable source for each turns up.

After reading a changed source and updating the shard by hand, refresh the fingerprint:

```bash
node scripts/refresh/watch-sources.ts --accept
```

### Link health

`npm run check:links` fetches every external URL the repo ships — from tile "Learn more" lists, shard citations, and these docs — and reports three things separately:

| Result | What it means |
|---|---|
| **Broken** | A 4xx/5xx, a DNS failure, or a refused connection. The link is dead. |
| **Redirected** | The canonical URL moved. **Not a pass:** agencies reuse article ids, so an old link can land on a page that is authoritative, plausible, and about something else entirely. |
| **Unreachable** | The server did not serve a complete certificate chain and the gap could not be closed. This category is now narrow on purpose: an **expired** certificate, one issued for another hostname, and a self-signed one are reported as **broken**, because a browser refuses all three and the reader gets an interstitial rather than the page. They used to land here, under a sentence promising the page was almost certainly fine. Both checks now repair the ordinary case the way a browser does — follow the leaf's AIA pointer, verify the fetched intermediate against Node's root store, retry — so this is left only for a chain no pointer repairs. The page is almost certainly fine; open it before replacing it. As of 2026-08-30 there are none. |

[`check-links.yml`](../.github/workflows/check-links.yml) runs it monthly and opens an issue on broken or redirected results. It is deliberately not part of the unit CI: it needs the network, and a suite that fails when a state revenue site has a bad afternoon is a suite people learn to ignore.

**Twenty-three of eighty shards were watched by nothing (2026-08-30).** The adapter check reports on the adapters that exist; it has nothing to say about a shard that has *no* adapter, so a dataset watched by nothing was invisible to the one report that would have named it. Nobody could have produced the count from the repo. It was twenty-three.

Nine are the no-income-tax states, which genuinely have nothing to index — a state adopting an income tax changes the shard's shape, not a number in it. The rest are not decisions, they are unwritten work, and five of them are pointed: **`capital-gains`, `eitc-ctc`, `gift-tax`, `amt` and `child-tax` all cite `rp-25-32.pdf`, the annual inflation-adjustment revenue procedure that the federal income-tax adapter already fetches and parses every month for the brackets.** Two more (`retirement-limits`, `ira-deduction`) cite the retirement-limits notice, a document of exactly the kind this pipeline reads. *Watch what you cite* was the invariant that fixed twenty-one adapters; these seven were behind it the whole time and nothing pointed at them.

[`watch-coverage.json`](../scripts/refresh/watch-coverage.json) now accounts for every dataset — watched by an adapter, watched for change, or listed with the reason neither fits — and a test fails if a new shard arrives with none of the three. The list is meant to **shrink**, and it drops an id automatically the moment something starts watching it, because leaving one there after an adapter lands tells the next reader a watched shard is unwatched, which is the same lie as the reverse. The reasons say plainly which entries are gaps rather than decisions; a list where work goes to be forgotten is worse than no list. **`gift-tax` came off it the same day**, which is the point: it now reads `rp-25-32.pdf` directly — the annual exclusion, the non-citizen-spouse exclusion and the basic exclusion amount, each anchored on the shard's own year, which the procedure prints in every section. That year anchor is what makes it safe to watch a document whose URL carries its own number: a procedure that does not state the shard's year is refused by name rather than read, which is the rule the federal adapter learned after three years on a frozen Rev. Proc. 2023-34. Dry-run to a no-op against the committed figures. **`amt` followed the same day.** Its section prints three tables, and they have to be read as three: "Married Individuals Filing Separate Returns $70,100" is the exemption and "Married Individuals Filing Separate Returns $122,250" is the 28% threshold, eighty words apart under the identical label, so a document-wide search writes one into the other's field and looks entirely healthy doing it. Each table is narrowed to its own lead-in first — the Maine and Wisconsin lesson — "Estates and Trusts" is dropped rather than becoming a filing status, and only the first amount after each label is taken, because the phase-out table prints the complete-phaseout amount in the column beside the threshold. A live no-op proves nothing on its own here (a parser that writes back what it was handed produces one too), so a test moves the printed figures and checks they land. `capital-gains` followed, where each row prints two amounts that are the CEILINGS of the 0% and 15% bands — exactly the lower bounds of the shard's 15% and 20% tiers — so a row yielding one amount is refused rather than half-written, which would leave the right shape with one bound from the wrong column. Finally `eitc-ctc`, whose table is the one that had to be read against its own header: the columns run **One, Two, Three or More, None** — None LAST — so walking the amounts in the order the shard stores them would give a childless filer the one-child credit and a three-child filer $664, four plausible numbers in the wrong rows, every field, every year. A header this does not recognise is refused rather than read positionally, and a test reorders the columns to prove the header is what drives it. **All five shards that cited rp-25-32.pdf now read it**, and the two that cite Notice 2025-67 followed: `retirement-limits` and `ira-deduction`. That notice writes every figure as a *movement* — "is increased from $23,500 to $24,500", or "remains $11,250" — so a pattern taking the first dollar amount after a section reference writes **last year's** limit in as this year's, a number wrong by exactly one year and entirely reasonable-looking. Both forms are matched and only the new value taken. The first attempt bounded each figure to a fixed 420 characters, which ran past "remains $11,250" into the next sentence and anchored the defined-contribution limit as the age-60 catch-up; it reads to the end of the figure's own sentence now, and takes whichever form appears first rather than preferring one by order of testing. Six of the ten retirement limits are stated there; the HSA and FSA figures come from other documents, which the shard's citation has always said, and are left exactly as committed. Then two of the list's own **reasons turned out to be wrong**, in opposite directions, and both were corrected the same day. `savers-credit` was described as "stated on an IRS web page": its nine AGI caps are in Notice 2025-67, the document the pipeline now fetches, and it has an adapter — one whose whole difficulty is that all three filing-status sentences open with the *same* section reference, § 25B(b)(1)(A), so a lookup keyed on the section writes the joint cap into every status and tells a single filer they qualify at twice the AGI they do. For a cliff credit that is the difference between $1,000 and nothing. (The source also drops a page number into the middle of "head of household", which the pattern allows for.) `education-credits` was described as indexing: § 25A(i) **fixed** its phase-out ranges and the 2020 Act aligned the Lifetime Learning range to the same figures, so there is no annual figure to chase — Delaware's shape, wanting a change-watch. **No entry on the coverage list is flagged as a gap any more**, and four more came off it the same day for the reason their own text gave: `social-security-taxation`, `education-credits`, `rmd-uniform-lifetime` and `social-security` each said they "belong on the change-watch" and were not on it. Each is now watched at the thing that would have to change — the statute on Cornell LII for §86, §25A and 42 U.S.C. §416(l), the regulation on eCFR for the Uniform Lifetime Table — matching precedents already on that list rather than at a publication like Pub 915 or Pub 590-B, which are reissued every year and would fire annually about rules that had not moved. "Belongs on the change-watch" is not a reason to be unwatched; it is a description of the work. **The list is down from twenty-three to eleven: nine no-income-tax states, plus `aca` and `fafsa`, whose sources are reissued annually at a new path each year and whose watch needs a page that lists the current one.** That a list of reasons had two wrong reasons in it is left recorded in the file rather than quietly edited away: a reason is a claim like any other, and a list of unchecked claims about why things are not checked is the last place anyone would think to look for an error. The dependent standard deduction joined on the same day, anchored on § 63(c)(5) rather than on its value, because the identical $1,350 is printed nine thousand characters earlier under the kiddie-tax section — two rules that agree today and are not the same rule.

**CPI's 2025 annual average said Jan–Sep and is not (2026-08-30).** A full dry run of the refresh pipeline — every group, not just the parser check — put the BLS CPI adapter back in reach: its keyless API spends a daily quota against a shared IP, and the quota had reset. It reports `no-op`, so the shard's **321.943 is right**. Its citation note was not. It read "the 2025 figure reflects the Jan-Sep average; the October 2025 release was delayed by the 2025 appropriations lapse", and BLS has since published November and December. The annual average is now the mean of the **eleven** months that exist, which is exactly 321.943; a Jan–Sep mean is **321.466**, so a reader checking the figure against the note it ships with would have made the site wrong by half a point on the series every inflation calculation runs through. October 2025 is also not delayed — the lapse stopped collection, so that month was never gathered and the gap is permanent. The note now says both, and the adapter joined the watched baseline: since an unreachable source no longer counts as a regression even on that list, a quota-limited API can be watched without a monthly false alarm.

**Medicaid's expansion map, audited and now watched (2026-08-30).** The `medicaid-2024` shard's threshold — 138% of the poverty line — has not moved since 2014, and its adapter watches that. What actually changes is the *map*: NFIB v. Sebelius made expansion optional, so a ballot measure or a legislature can flip a state, and telling a household in a non-expansion state that it may qualify is the worst answer this shard can give. Nothing was watching the map. The shard's own citation note said "a state can also change its position by ballot measure or legislation, which is what the refresh watch is for", and no watch covered it.

The map is now audited and watched. CMS's [Medicaid, CHIP and BHP eligibility levels](https://www.medicaid.gov/medicaid/national-medicaid-chip-program-information/medicaid-childrens-health-insurance-program-basic-health-program-eligibility-levels) table is the only Medicaid.gov page that states it in readable text — one row per state, with an "Expansion to Adults" column reading a percentage or `No` — and every one of the 51 jurisdictions was checked against it row by row on 2026-08-30. **All 51 agree.** It joins the change-watch rather than getting a parser, for the reason the watch list records: the table is dated "based on state decisions as of December 1, 2023", so a parser reading it would confirm a 2026 shard forever and could never report a change. That is the Rev. Proc. 2023-34 trap, and fingerprinting is the honest half of the guarantee — CMS republishing the table is what a state changing position looks like here, and a person reads the diff.

One open item that audit turned up, recorded rather than guessed at: the shard's District of Columbia override carries **215%** of the poverty line, and the CMS table's DC row reads **210%** as of December 2023. Both are plausible — DC's is the most generous threshold in the country and it has been raised more than once — and the CMS table is three years old, so it cannot settle a 2026 figure either way. It wants a reviewer against DC's own Department of Health Care Finance publication, not a scrape and not a guess.

**Note for the next state refresh.** Several state adapters' `sourceUrl`s were repointed at live pages after their originals rotted (NY, GA, IL, MI, IN, MT, ME, MS, MD, AR). Their parsers anchor on text in the *old* pages and have **not** been re-validated against the new ones. That is safe rather than silent: a parser that cannot find its anchors takes the fail-safe path and opens an alert PR instead of writing data, which is exactly what should happen. Expect that on the next run for those states, and re-anchor the parser then.
